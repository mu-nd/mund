# 設計メモ(2026-11-16 打ち合わせ議事録反映版)

このリポジトリの設計判断をまとめた文書です。**(a) 既存仕様**(これまでの議論と、
2026-11-16 の打ち合わせの議事録で決まっていたこと)、**(b) 課題**、
**(c) 新規提案**(今回の実装で仮に決めたこと)を区別して書きます。
(c) は動くものを作るために置いた仮決めであり、確定仕様ではありません。変更したい点は
末尾の「確認していただきたいこと」を見てください。

## 2. データファイル

### データ1件の形 【(a)】

項目名と入れ子は、川瀬さんが muND 用に作成した JSON Schema
([shkawase/mund](https://github.com/shkawase/mund))に合わせています。

```json
{"datasetId": "e2551c5951a7",
 "nuclide": {"element": "Si", "mass": 28, "isomer": 0},
 "observable": {"kind": "lifetime",
                "lifetime": {"value": 743.9, "unit": "ns",
                             "uncertainties": [{"source": "total", "value": 5.0}]}}}
```

| 項目 | このリポジトリでの扱い |
|---|---|
| `datasetId` | 12桁のハッシュ(DataID)。UUID は長すぎるため、3節の決定論的 ID にした |
| `datasetType` | experiment / theory / curated / evaluated。ファイル先頭に1回書く。ディレクトリ名と ID には EXP / TH / CUR / EVAL を使う |
| `nuclide` {element, mass, isomer} | mass 0 = 天然同位体比 |
| `observable` {kind, 値のブロック} | kind は lifetime / capture_rate / capture_probability(τ・Λcap・Bcap) |
| `uncertainties` [{source, value}] | 統計と系統を分けて書ける。source は total / statistical / systematic / other |
| `bibId` | DOI。DOI のない文献は仮 DOI `10.1000/mund.<名前>` |
| 実験条件への参照 | `meta.id`(MetaID)。論文1本につき1つで、データと同じファイルに置く(下記) |
| 文献情報 | `data/master/bibliography.json`。Crossref の項目名のまま必要部分を保存 |
| Huff factor などのパラメータ | `data/master/` に置き、データと同じくバージョン管理する。核の質量・崩壊データ・天然存在比などは収録しない |
| 実験データ | τ・Λcap・Bcap のうち、論文に最も近い量を1つ |
| キュレーションデータ | Λcap。元にした実験データを `originalData` に必ず書く |
| 評価データ | Λcap。元にしたキュレーションデータのセットを `meta.referenceDatabase` に書ける(任意)。個別の ID を挙げたい場合は `originalData` も使える |
| メタデータ | facility は一覧から選択、method は LT の選択肢(electron / gamma / neutron / charged particle / fission fragment)を候補表示、beam・target・detector は自由記述 |
| サブライブラリ名 | XR / LT / ES / BR(以前の文書の XEI / NCR / ESP / RPB)。論文 arXiv:2605.15539 の名称を採用 |

元のスキーマと違う点は2つです。

1. **保存の単位。** リポジトリでは、メタデータ1件(= 論文1本)と、それを参照するデータを
   **1つのファイル**にまとめ、`datasetType`・`bibId`・実験条件はファイルの先頭に1回だけ書きます。
   議事録の「メタデータは論文1本につき1つ、DOI をキーに、必要なら枝番」をそのまま
   ファイル単位にしたものです。論文を1本登録する = ファイルが1つ増える = コミットが1つ、となります。
   **公開用の `LT.json` では、1件ずつ自己完結した形**(`datasetType`・`bibId`・`metaId` 付き)に
   展開されます。
2. **不確かさの値は数値。** 文字列ではなく数値で持ちます。非対称誤差・相対誤差・上限下限は、
   LT では当面不要と判断して入れていません(7節)。

### ファイル形式: JSON 【(a) JSON Schema + (c) 書式】

- 元素記号 `No`・`Y`・`N` などが YAML では真偽値と解釈されうる(パーサによって挙動が違う)。
- Monaco Editor が JSON Schema に基づく入力チェックと補完を標準で持っている。
- 配布形式(JSON / CSV)と元データが同じ形式になり、変換層が要らない。

「読みやすさ・差分の追いやすさ」は書式で担保しています(`docs/data-format.md` 4節)【(c)】:
**データは1行に1件**、メタデータは1項目1行。値を1つ直すと差分は1行だけになります。
読み書きは `jsonfmt`(Python / JS 各1ファイル)に集約してあるので、YAML 等への差し替えは局所的です。

ファイル名は `<第一著者><年>_<MetaID>.json`。前半は人が読むための目印で、識別は MetaID です。

### 数値は「書かれたとおり」に保存 【(c)】

`13.250` と入力すれば `13.250` のまま保存されます(JSON としては普通の数値です)。
論文に書かれた有効桁を失わないためです。表示もこの桁数に従います。

### 単位は ASCII 【(a) 元のスキーマの `us`・`ns` を踏襲、捕獲率は (c)】

`us`(マイクロ秒)、`us-1`(毎マイクロ秒)。µ には見た目が同じ別の文字(U+00B5 と U+03BC)があり、
機械処理で事故のもとになるためです。画面上は µs⁻¹ と表示します。

### 不確かさ 【(a) 形式 + (c) 合成方法】

`uncertainties` に `total`(全体)または `statistical`・`systematic`(分けて書かれている場合)を並べます。
記載がなければ空の配列です。換算値やグラフのように不確かさが1つ必要な場面では、`total` があれば
それを、なければ各成分の二乗和を使います。入力ツールには「統計・系統誤差を分けて入力」の列があります。

### 文献データベース 【(a)】

`data/master/bibliography.json` に、DOI をキーとして Crossref の JSON の必要部分(著者・表題・誌名・
巻・ページ・年)を**Crossref の項目名のまま**保存します。入力ツールで DOI を入れて「書誌情報を取得」を
押すとここに追加されます。DOI のない文献は、仮 DOI `10.1000/mund.<名前>` のもとに同じ形の項目を
手で作ります。公開サイトは Crossref に問い合わせずに表示できます。

### 関連 DOI 【(a) 議事録】

メインの DOI を1つ決め(`bibId`)、arXiv・訂正・データリポジトリなどは `relatedBibIds` に並べます。
ID に入るのはメインの DOI だけです。

## 3. ID 【(a)。詳細は `docs/id-definition.md`】

```
MetaID            = SHA-256("LT|{DataSet}-META|{DOI 大文字}[|{KEY 大文字}]") の先頭12桁
DataID(datasetId) = SHA-256("LT|{DataSet}|{元素}|{質量数×1000}|{MetaID}[|{KEY 大文字}]") の先頭12桁
                    DataSet は EXP / TH / CUR / EVAL
```

この規則が、リポジトリ作成前から使われていた ID(MetaID 3件、DataID 67件)を再現することを
確認しています。これらは `tests/vectors/ids.json` に入っており、Python 実装と
ブラウザ実装の両方が毎回これで検証されます。

- (b) 課題だった「メタデータを書き換えると ID が変わる」問題は、この規則で解消しています。
  施設・手法・コメントなどは ID に入りません。
- (b) キュレーションデータの以前の ID は `CUR` ではなく `TH` で計算されていました。
  規則どおり `CUR` で計算し直し、旧 ID は `legacyIds` に残しています。
- (c) 元素・質量数・Key・DOI を訂正して ID が変わる場合、入力ツールが旧 ID を `legacyIds`
  に記録し、その ID を `originalData` で参照している他のファイルも自動で書き換えます。
- 同じ核種のデータ点が1つのメタデータに複数ある場合は Key で区別します(重複するとエラーになります)。
  アイソマーは ID に入らないので、アイソマーを区別する場合も Key を使います。

## 4. バージョン 【(a) 方針、(c) 具体化。詳細は `docs/versioning.md`】

議事録の要望:「Web に出すのはメジャーバージョンだけ。外部の人には固定版を見せ、
開発中は latest を選べるように。履歴は Git で全部追える」。

- 公開サイトは、タグ `vN.0.0` ごとに固定版 `vN` を作り、既定でいちばん新しい固定版を表示。
- `latest`(main ブランチの現在の状態)はバージョン選択で選べる。
- パッチ・マイナーは Git のタグと CHANGELOG に残るだけで、サイト上のフォルダは増えない。
- 固定版は「そのタグ時点のツール」でビルドするので、後から形式を変えても過去の版は変わらない。
- まだリリースが1つもないので、現在のサイトは latest(開発版)を表示します。
  **最初の公開版にするときは、入力ツールの「リリース」で メジャー → v1.0.0 を作ってください。**

## 5. 入力ツール(管理者向け UI)

議事録で最優先とされたものです。「触ってセーブすると、誰がいつどこを書き換えたかが
記録される」を次の形で実現しています。

- 静的ページ(`/admin/`)からブラウザが直接 GitHub API を呼ぶ。サーバは不要。
- 認証は各自の GitHub アクセストークン(Fine-grained PAT)。コミットはその人の名前で記録される。
- 変更はいったんブラウザ内の下書きになり、差分を確認してから**1つのコミット**として送る。
  直接コミットのほか、ブランチ + Pull Request にもできる(レビューしてから反映したい場合)。
- 他の人が同じファイルを先に更新していた場合は上書きせず、コミットを拒否する。
- 入力チェックは CI と同じ規則をブラウザ内で実行(スキーマ、ID、参照関係、施設名)。
- 統計誤差・系統誤差を分けて入力できる。
- 入力ミス対策: 換算値の表示と、評価値(EVAL)との比較による「⚠ 要確認」表示。
  初期データで見つかったような元素記号の取り違えは、ここで気付けます。
- 練習モード: GitHub に一切送らずに全操作を試せる。

## 6. 公開サイト(Explorer)

旧 Explorer の構成を踏襲しています: サブライブラリ切替、データ種別の複数選択、
元素・質量数での絞り込み、`?z=` による元素指定、一覧と可視化、寿命 ⇄ 捕獲率 ⇄ 捕獲確率の換算
(★ が出典に書かれた量)、文献リンク(DOI)、CSV ダウンロード、Muon Lifetime Converter。
追加したもの: CUR から元の EXP へたどる表示、ID・ソースファイル・変更履歴へのリンク、
バージョン選択、ダウンロードページ。

`https://ribf.riken.jp/muon/` の周期表リンクは `./db/?z=14` の形なので、リンク先の先頭を
GitHub Pages のアドレスに変えるだけでそのまま使えます(`docs/deployment.ja.md`)。

## 7. 確認していただきたいこと

決めていただければすぐ反映できます。

1. **初期データで訂正した4件**(Be→B 2件、Si→S、In→I)が正しいか(`docs/migration-notes.md`)。
2. **実験条件の Beam / Target / Detector** は、このリポジトリ用に書いた短い要約です。内容の確認をお願いします。
3. **データのライセンス**(CC BY 4.0 等)。未定のため、サイトには「未定」と表示しています。
   ソフトウェアは MIT としています。
4. **仮 DOI の形**: DOI のない文献は `10.1000/mund.<名前>` としました。
   既存の `10.1000/unpublished`(キュレーション論文が出るまでの仮置き)はそのままです。
5. **不確かさの拡張**: 現在は対称な誤差(全体、または統計・系統)のみ。非対称誤差・上限下限・共分散は
   BR で必要になるはずなので、そのときに川瀬さんのスキーマの表記を基に追加します。
6. **Evaluated の `referenceDatabase`** の書き方(例: `muND LT curated v1.0.0`)。
7. **理論データの計算条件**: 専用の項目は設けず、theory のメタデータに method と comment だけを持たせています。
8. **施設一覧**: これまでの一覧を引き継いでいます。追加・変更があれば反映します
   (例: Super-Kamiokande を `Cosmic` に含めるか、独立させるか)。
9. **Huff factor の表の出典**: 旧 Explorer が使っていた表をそのまま収録しています。
   出典(文献)を `data/master/huff_factors.json` に明記したいので、教えてください。
10. **XR / ES / BR のデータ形式と ID**: 未着手。BR は、分母(stopped muon か muon capture か)、
    Cumulative / Independent の区別、下限値の扱いの決定が必要です。
11. **リリースごとの DOI**(Zenodo 連携): 未設定。
