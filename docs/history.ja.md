# 経緯と未決事項

過去の経緯と、まだ決まっていないことは、この文書だけに書きます。
ほかの文書(`README.md`、`docs/` の仕様と手引き)は、いまある仕組みの説明です。

## 1. 設計のもとになった決定(2026-11-16 の打ち合わせ議事録)

- サブライブラリは XR / LT / ES / BR の4つ、データ種別は EXP / TH / CUR / EVAL の4つ。
  種別は改訂の段階ではなく、別々のデータである。
- データとメタデータを分け、DataID と MetaID で結ぶ。ID は決定論的で、値や不確かさを含めない。
- メタデータは論文1本につき1つ。DOI をキーにし、必要なら枝番(Key)を付ける。
  メインの DOI を1つ決め、arXiv 版などは関連 DOI とする。
- マスターデータは GitHub に置き、差分で管理する。編集は UI から行い、
  誰がいつどこを書き換えたかが記録されるようにする。これを最優先とする。
- 公開は静的サイト(HTML と JavaScript)で行う。
- Web に出すのはメジャーバージョンだけ。外部の人には固定版を見せ、開発中の状態は latest として選べるようにする。
- 版番号は 0.0.1 から始める(2026-11-19 に決定。それまでの 0.1.0 はタグも公開もしていない)。最初の正式公開で 1.0.0 にし、
  固定版 v1 として公開する。
- 形式と ID が決まっているのは LT だけ。XR / ES / BR は未確定で、先に決めない。

## 2. 設計上の選択と理由

- **項目名と入れ子**は、川瀬さんが muND 用に作成した JSON Schema
  ([shkawase/mund](https://github.com/shkawase/mund))に合わせた。違いは次の2点。
  - 保存の単位: メタデータ1件(論文1本)と、それを参照するデータを1つのファイルにまとめた。
    論文を1本登録すると、ファイルが1つ増え、コミットが1つできる。
    公開用の `LT.json` では、データ1件ずつが自己完結した形に展開される。
  - 不確かさの値は文字列ではなく数値。非対称誤差・相対誤差・上限下限は形式1の範囲外とした
    (既存の LT データには現れない。不要と判断したのではなく、必要になったときに表記を決める。8節)。
- **JSON**(YAML ではなく): 元素記号 `No`・`Y`・`N` が YAML では真偽値と解釈されうる。
  Monaco Editor が JSON Schema による入力チェックと補完を備えている。配布形式と同じ形式なので変換が要らない。
- **データは1行に1件**: 値を1つ直すと差分が1行になる。
- **数値は書かれたとおりに保存**: 論文の有効桁を失わない。
- **単位は ASCII**(`us`、`us-1`): µ には見た目が同じ別の文字(U+00B5 と U+03BC)がある。
- **UUID ではなく12桁のハッシュ**: UUID は長すぎるという判断。
- **サブライブラリ名**は論文 arXiv:2605.15539 の XR / LT / ES / BR
  (それ以前の文書では XEI / NCR / ESP / RPB)。
- **検証・整形・ID・換算は Python と JavaScript の両方にある**: コマンドラインと CI は Python、
  入力ツールはブラウザで同じ規則を使う。両者は共通のテストベクトル(`tests/vectors/`)で一致を確認している。
- **固定版は、リリースのときに一度だけ作って保存する**(`releases/vN/`、ハッシュ付き)。
  当初は「そのタグ時点のツールで毎回ビルドし直す」方式だったが、2026-11-17 の独立設計レビューで、
  古いツールが将来も動く前提に依存し、公開されるファイルが同じである保証がないと指摘されたため改めた。
  あわせて、CI が検査したコミットと公開するコミットを一致させ(以前はタグで起動したときに main をビルドしていた)、
  公開の再試行は元のリリースコミットにだけタグを付けるようにした(以前は再試行時点の最新状態に付けていた)。

## 3. ID の経緯

- 最初の案は、元素・質量数・**値**・DOI から1つの ID を作るものだった。値を直すたびに ID が変わるため、やめた。
- 現在の規則(`docs/id-definition.md`)は MetaID と DataID を分け、値を含めない。
  このリポジトリを作る前から使われていた ID(MetaID 3件、DataID 67件)を再現することを確認しており、
  それらは `tests/vectors/ids.json` に入っている。
- キュレーションデータの以前の ID は、`CUR` ではなく `TH` で計算されていた。
  規則どおり `CUR` で計算し直し、以前の ID は `legacyIds` に残した。
- 評価データの以前の ID はランダムな8文字だった。規則どおりの ID に置き換え、以前の ID は `legacyIds` に残した。

## 6. 入力ツール

- 最初はブラウザから GitHub API を直接呼ぶ形で、公開サイトの `/admin/` に置いていた
  (各自の GitHub アクセストークンを使用)。
- 2026-11-17、データを入力するのは少数の研究者で、各自の PC で動かせば足りることから、
  手元で動かす形に改めた。目標は「研究者向けの VS Code + Git の簡易版」:
  ファイルを開いて保存を押すと、検証・記録(git commit)・GitHub への送信(git push)まで行い、
  git を意識しなくてよいこと。
- 環境(Python、jsonschema、git、GitHub CLI)は pixi(conda-forge)で用意する。
  Julia の Pkg と JLL で git・gh を入れるのと同じ考え方。

## 7. 独立設計レビュー(2026-11-17)への対応

構成(Git 管理の JSON、静的な利用者画面、手元で動く管理画面)は変えず、次を改めた。

- **データを壊しうる操作**: 管理画面が行の対応を配列の位置で判断していたため、行の並べ替えで
  `legacyIds` と CUR の `originalData` が別の行に付け替わりえた。既存の datasetId で対応を取り、
  ID が変わる変更は「同じ記録の訂正」か「別のデータ」かを人が選ぶ形にした。未知の単位が既定の単位に
  書き換わる問題、保存のあと送信中の編集も含めて下書きが全部消える問題も直した。
- **派生値の入力の版**: `originalData` を datasetId だけでなく、使った時点の内容ハッシュ(`entryHash`)と
  組で記録するようにした。既存の CUR 8件には、この変更の時点の EXP の内容ハッシュを記録した
  (つまり「この時点の EXP から作られた」とみなしている。実際に作ったときの EXP と同じかは、記録がないため確認していない)。
- **初期データの訂正4件**(4節)を、各エントリーの `corrections` に構造化して記録した
  (訂正前の値、理由、以前の ID、論文との照合は未了 = `checkedAgainstSource: false`)。
- **形式1の範囲を明示**: CUR / EVAL は捕獲率だけ(既存データはすべて捕獲率)、核種は基底状態だけ
  (`isomer` は 0。異性体が ID にどう入るかが決まっていないため)。どちらも既存データには影響しない。
- **換算の入力の検査**: 定数の重複(Python は後のものを、JavaScript は先のものを使っていた)、
  `mu_plus_lifetime` の欠落・単位違い・負値、Huff 表の重複を両言語で同じように拒否するようにした。
  換算ページで Q に数値でないものや負値を入れると、黙って表の値で計算していたのを、エラー表示にした。
- **論文からの独立二重抽出・照合・裁定**を管理画面に加えた(作業場所は `data/` の外。承認済みのものだけが `data/` に入る)。

## 8. 未決事項

決めていただければ反映します。

1. **初期データで訂正した4件**(4節)が正しいか。照合したら各エントリーの `checkedAgainstSource` を `true` にする。
2. **実験条件の Beam / Target / Detector の要約**の内容。
3. **データのライセンス**(CC BY 4.0 など)。未定。サイトのページにはライセンスを書いていない(Downloads の記載は 2026-11-19 に削除)。
   `dataLicence` は、決まるまで選択範囲の JSON では「to be decided」、API のファイルでは `null`。ソフトウェアは MIT。
4. **DOI のない文献の仮 DOI** の形(現在は `10.1000/mund.<名前>`。既存の `10.1000/unpublished` はそのまま)。
5. **不確かさの拡張**: 現在は対称な誤差(全体、または統計・系統)だけ。非対称誤差・上限下限・共分散は
   BR で必要になる見込みで、そのときに川瀬さんのスキーマの表記をもとに追加する。
6. **評価データの `referenceDatabase`** の書き方(例: `muND LT curated v1.0.0`)。
7. **理論データの計算条件**: 専用の項目はなく、メタデータの method と comment だけ。
8. **施設一覧**: これまでの一覧を引き継いでいる(例: Super-Kamiokande を `Cosmic` に含めるか、独立させるか)。
9. **Huff factor の表の出典**: 以前の Explorer が使っていた表をそのまま収録している。
   出典(文献)を `data/master/huff_factors.json` に明記したい。
10. **XR / ES / BR の形式と ID**: 未着手。BR は、分母(stopped muon か muon capture か)、
    Cumulative / Independent の区別、下限値の扱いを決める必要がある。
11. **リリースごとの DOI**(Zenodo 連携): 未設定。
12. **紹介・ニュース・メンバーの内容**: 文面は ribf のページ(2026-11-19)のまま。「under construction」の表示は載せていない。
    ribf の物理の解説ページ(`docs/` の概要・XR・LT・ES・BR)を muND の Docs に取り込むか、その場合に数式をどう表示するか
    (サイトは外部から何も読み込まない方針で、MathJax を使うならこの方針を変えることになる)は未定。
