# 経緯と未決事項

過去の経緯と、まだ決まっていないことは、この文書だけに書きます。
ほかの文書(`README.md`、`docs/` の仕様と手引き)は、いまある仕組みの説明です。

## 1. 2026-11-16 の打ち合わせ(議事録)

- サブライブラリ4つ(X 線エネルギー・寿命・エネルギースペクトル・分岐比。このリポジトリでは XR / LT / ES / BR)と、
  データ種別4つ(実験・理論・キュレーション・評価。EXP / TH / CUR / EVAL)の 4 × 4。種別は別々のデータとして持つ。
  原子核1つに値が1つで最も簡単な LT から始める。
- マスターデータは、差分を git で追えるテキストのファイルにして GitHub に置く(JSON か YAML かにはこだわらない)。
  川瀬さんが作った JSON Schema のプロトタイプから始める。
- 入力は UI から行い、保存すると誰がいつどこを書き換えたかが記録されるようにする。入力する人はほぼ1人。
- メタデータは論文1本につき1つで、データはメタデータの ID で結ぶ。メインの DOI を1つ決め、arXiv 版やデータの DOI は関連 DOI とする。
  1本の論文に別々の測定があるときは枝番(Key)を付け、ID はデータ種別と DOI(と枝番)のハッシュで作る。
- ID は短くし(UUID は長すぎる)、記録を更新しても変わらないものにする(変わると履歴がたどれない)。
- 文献の書誌は手で書かず、DOI から Crossref で取る。表示は「著者 年」の形で、クリックすると原典に飛べるようにする。
- DOI のない文献には、DOI として存在しない私的な識別子を振る。他人の論文に DOI を振ったり、理研のドメインで振ったりはしない
  (DOI の使われていない番号帯を使う案が出た)。
- 施設は一覧から選ぶ(1960 年代の施設や Super-Kamiokande も含める)。ビーム・標的・検出器・手法は自由記述
  (標的のガス・化学状態・濃縮度など)。コメント欄を設ける(例: NaCl の標的で測った Cl のデータに Na の情報を添える)。
- 実験データ(EXP)は原典に近い値を入れる。キュレーション(信用できる実験値を選んだもの)と評価は、換算(τμ+ の値など)を
  統一して計算し直す。キュレーションは論文にまとめ、その DOI をキュレーションデータの文献にする。
- 寿命・捕獲率・捕獲確率の換算がほしい。表は CSV でダウンロードできるようにする。入口は周期表で、元素を押すとデータに進む。
- 公開は GitHub Pages の静的サイト(HTML と JavaScript)で行い、`ribf.riken.jp/muon/` のトップページと URL は保つ
  (カスタムドメインかリンクで GitHub 側に進む)。変更履歴は GitHub で見られるようにする。
- 版は、小さな訂正はパッチ、データの追加はマイナー、壊す変更はメジャーで上げる。Web に出すのはメジャーバージョンだけで、
  外部の人には再現できるよう固定版を見せ、開発中の状態は latest として選べるようにする。

## 2. 設計上の選択と理由

- **項目名と入れ子**は、川瀬さんが muND 用に作成した JSON Schema
  ([shkawase/mund](https://github.com/shkawase/mund))に合わせた。違いは次の2点。
  - 保存の単位: メタデータ1件(論文1本)と、それを参照するデータを1つのファイルにまとめた。
    論文を1本登録すると、ファイルが1つ増え、コミットが1つできる。
    公開用の `LT.json` では、データ1件ずつが自己完結した形に展開される。
  - 不確かさの値は文字列ではなく数値。非対称誤差・相対誤差・上限下限は形式1の範囲外とした
    (既存の LT データには現れない。不要と判断したのではなく、必要になったときに表記を決める。8節)。
- **DOI のない文献の bibId**(2026-11-21): [NSR](https://www.nndc.bnl.gov/nsr/)(原子核分野の文献索引)のキー番号
  (`NSR:1987SU06`)、NSR にもない文献は muND 独自の名前(`muND:Suzuki1975thesis`)。打ち合わせの案(DOI の使われていない
  番号帯)は、どの番号帯も将来割り当てられうるうえ、使っていた `10.1000` は DOI Foundation 自身の番号帯だった。NSR のキー番号なら
  NSR のページにリンクでき(muND の 3 本の論文もすべて NSR にある)、muND の名前の文献は書誌情報の `URL` からリンクする。
  DOI の文献も `DOI:10.1103/vl7z-rzp8` とし、3 つの形を「前置き:名前」にそろえた(対称性のため)。書誌情報はすべて `id`(= bibId)で引く。
- **JSON**(YAML ではなく): 元素記号 `No`・`Y`・`N` が YAML では真偽値と解釈されうる。
  Monaco Editor が JSON Schema による入力チェックと補完を備えている。配布形式と同じ形式なので変換が要らない。
- **JSON の読み込みは厳密**(2026-11-22): 同じ名前の項目が2回ある、または範囲外の数値(`1e400` など)は、Python と JavaScript の
  どちらでも誤りにする。値が黙って捨てられたり無限大になったりしないため。
- **データは1行に1件**: 値を1つ直すと差分が1行になる。
- **数値は書かれたとおりに保存**: 論文の有効桁を失わない。
- **単位は ASCII**(`us`、`us-1`): µ には見た目が同じ別の文字(U+00B5 と U+03BC)がある。
- **サブライブラリ名**は論文 arXiv:2605.15539 の XR / LT / ES / BR
  (それ以前の文書では XEI / NCR / ESP / RPB)。
- **検証・整形・ID・換算は Python と JavaScript の両方にある**: コマンドラインと CI は Python、
  入力ツールはブラウザで同じ規則を使う。両者は共通のテストベクトル(`tests/vectors/`)で一致を確認している。
- **XR / ES / BR の雛形**(`templates/`、2026-11-21): 形式が決まるまで、ページを設計するための形の案を JSON Schema で置く。
  残す価値があるのは値ではなく形なので(リポジトリの外の架空のファイルでは、形の変更が記録に残らず、ほかの人も使えない)、
  架空の値のファイルは `templates/make_examples.py` で必要なときに作り、雛形に合うことをテストで確かめる。外枠とメタデータは
  LT のスキーマを参照する。`schema/` に置かないのは、サイトに公開され、版の内容にも数えられるため。雛形は形式を決めたものではない。
- **版番号**: 2026-11-19 に `VERSION` を 0.1.0 から 0.0.1 にした(0.1.0 はタグも公開もしていない)。最初の正式公開で 1.0.0 にし、
  固定版 v1 として公開する。それより前の版番号を 0.0.1 と 0.0.0 のどちらから始めるかは未決(8節 21)。
- **固定版の `manifest.json`** が記録する元ファイルのハッシュは `sources` だけ(2026-11-22)。ビルドしたツールのハッシュは、
  読むものがなく、動いたコードではなくディスク上のファイルを測っていたため記録しない。
- **公開する版の一覧は `api/versions.json` だけ**(2026-11-22。同じ内容の `data/versions.json` は文書になく、やめた)。
- **定数表はオブジェクト**(`muND/constants/2`、最初のリリース前の 2026-11-22): 定数は `mu_plus_lifetime` の1つだけなので、
  リストをやめて欠落・単位・値の規則をスキーマで表し(重複は起こりえない)、そのための4つの検査コードをなくした。
- **モジュールの分け方**(2026-11-22): ビルドは1つの版のファイル(`build.py`)、固定版(`releases.py`)、サイト(`site.py`)に分けた
  (入力ツールは固定版の部分だけを使う)。サイトのページのスクリプトは `assets/js/pages/` に置き、ページのフォルダーと同じ名前にした。
- **pixi.lock はコミットせず無視する**(`.gitignore`)。pixi の Python は CI と同じ 3.13 に固定する。

## 3. ID の経緯

- 最初の案は、元素・質量数・**値**・DOI から1つの ID を作るものだった。値を直すたびに ID が変わるため、やめた。
- 現在の規則(`docs/id-definition.md`)は MetaID と DataID を分け、値を含めない。
  このリポジトリを作る前から使われていた ID(MetaID 3件、DataID 67件)を再現することを確認していた。
  DOI に `DOI:` を付けてから(下記)は、`tests/vectors/ids.json` の値は今の規則で計算し直したもの。
- キュレーションデータの以前の ID は、`CUR` ではなく `TH` で計算されていた。
  規則どおり `CUR` で計算し直し、以前の ID は `legacyIds` に残した。
- 評価データの以前の ID はランダムな8文字だった。規則どおりの ID に置き換え、以前の ID は `legacyIds` に残した。
- 2026-11-21、`bibId` を「前置き:名前」の形にしたため(2節)、MetaID 4件(キュレーションデータ `591344c27b81` → `15fd4fea826c`、
  DOI の文献 `dcb3b051457e` → `4d2ed5c83736`、`96f2c4a2ddaf` → `6c7ebc35077d`、`c93df5b12b00` → `194f28ccc0dc`)と
  DataID 655件が変わった。以前の ID は `legacyIds` に残し、キュレーションデータの元データの参照は新しい ID に付け替えた。
- 2026-11-22、`tools/mund.py fix` はすでにある ID を変えず、変わる場合は止まるようにした。以前は計算し直して上書きしていたため、
  以前の ID が `legacyIds` に残らず、元データの参照が切れていた。ID の変更は `legacyIds` を残す入力ツールで行う。

## 6. 入力ツール

- 最初はブラウザから GitHub API を直接呼ぶ形で、公開サイトの `/admin/` に置いていた
  (各自の GitHub アクセストークンを使用)。
- 2026-11-17、データを入力するのは少数の研究者で、各自の PC で動かせば足りることから、
  手元で動かす形に改めた。目標は「研究者向けの VS Code + Git の簡易版」:
  ファイルを開いて保存を押すと、検証・記録(git commit)・GitHub への送信(git push)まで行い、
  git を意識しなくてよいこと。
- 環境(Python、jsonschema、git、GitHub CLI)は pixi(conda-forge)で用意する。
  Julia の Pkg と JLL で git・gh を入れるのと同じ考え方。
- **保存の規則**(2026-11-22): 書き込む前に、git が保存する人(名前とメールアドレス)を知っていること、ツールの外で記録待ちにされた
  ファイルがないことを確かめ、書き込みか記録に失敗したら、すべてのファイルを保存前に戻す。記録されなかった変更が保存済みと扱われたり、
  関係のないファイルが一緒に記録・送信されたりしないため。ツールは1つのタブでだけ開く(2つのタブが互いの下書きを上書きしないため)。
- 画面は日本語と英語の2言語のまま(2026-11-22。日本語を読まない人が入力する場合に備えて)。

## 7. 独立レビューへの対応

独立設計レビュー(2026-11-17)を受けて、構成(Git 管理の JSON、静的な利用者画面、手元で動く管理画面)は変えず、次を改めた。

- **固定版は、リリースのときに一度だけ作って保存する**(`releases/vN/`、ハッシュ付き)。そのタグ時点のツールで毎回ビルドし直す方式は、
  古いツールが将来も動くことに頼り、公開されるファイルが同じである保証がないため。あわせて、CI が検査したコミットと公開するコミットを
  一致させ、公開の再試行では元のリリースコミットにだけタグを付ける。
- **データを壊しうる操作**: 管理画面が行の対応を配列の位置で判断していたため、行の並べ替えで
  `legacyIds` と CUR の `originalData` が別の行に付け替わりえた。既存の datasetId で対応を取り、
  ID が変わる変更は「同じ記録の訂正」か「別のデータ」かを人が選ぶ形にした。未知の単位が既定の単位に
  書き換わる問題、保存のあと送信中の編集も含めて下書きが全部消える問題も直した。
- **派生値の入力の版**: `originalData` を datasetId だけでなく、使った時点の内容ハッシュ(`entryHash`)と
  組で記録するようにした。既存の CUR 8件には、この変更の時点の EXP の内容ハッシュを記録した
  (つまり「この時点の EXP から作られた」とみなしている。実際に作ったときの EXP と同じかは、記録がないため確認していない)。
- **初期データの訂正4件**(4節)を、各エントリーの `corrections` に構造化して記録した
  (訂正前の値、理由、以前の ID、論文との照合は未了 = `checkedAgainstSource: false`)。
- **形式1の範囲を明示**: CUR / EVAL は捕獲率だけ(既存データはすべて捕獲率)、核種は基底状態だけ
  (`isomer` は 0。異性体が ID にどう入るかが決まっていないため)。どちらも既存データには影響しない。
- **換算の入力の検査**: 定数の重複(Python は後のものを、JavaScript は先のものを使っていた)、
  `mu_plus_lifetime` の欠落・単位違い・負値、Huff 表の重複を両言語で同じように拒否するようにした。
  換算ページで Q に数値でないものや負値を入れると、黙って表の値で計算していたのを、エラー表示にした。
- このレビューを受けて加えた論文の値の独立二重抽出(照合・裁定・承認)の機能は、削除した(2026-11-22、オーナーの決定)。
  打ち合わせで求められたものではなく、値は入力ツールで手で入力する。

2026-11-22〜24 には、再設計が仕様どおりにできているかを独立に確かめ、別の AI モデルによる独立レビューの指摘 322 件を
1件ずつ判断した。採った指摘は直し、テストで確かめた。構成は変えていない。データを読む人に関わる決定は次のとおり。

- **ID**: ID を計算するとき、Key は前後の空白を除き、ASCII の英字だけを大文字にする。ID の項目の区切り `|` は bibId と Key に使えない。
- **検査**: 自己矛盾する核種表(元素の並び、同じ原子番号の重複、元素表にない原子番号)と、原子番号より小さい質量数は誤り。
  元データは今の ID でも以前の ID でも指せ、同じ測定を両方の ID で2回挙げると誤り。
- **桁**: 原典の値と不確かさは原典の桁のまま示す。換算値は不確かさの桁に丸めた普通の数字で示す(990 ± 100)。
- **CSV**: 統計・系統の不確かさの列は、同じ種類の成分が複数あれば二乗和の平方根にまとめる(1つなら書かれた桁のまま)。
  行の終わりは LF で、カンマ・二重引用符・CR・LF を含む欄だけを引用符で囲む。
- **書誌の URL**: 小文字の `http://` か `https://` に空白でない文字が続くものだけを受け付け、リンクにする。
- **公開**: 版のタグは共有の main にあるコミットにだけ付ける。`build --out` が置き換えるのは、新しいか空のフォルダーか、
  以前のビルドの出力だと印(`.mund-build`)で確かめられたフォルダーだけ。
